# ブートシーケンス

[English](boot.md)

通信仕様：[CDCフラッシュ・プロトコル](flash.ja.md)

この文書は NextMicon Cherry のブートシーケンスをまとめたものです。

## イメージとコールドブート選択

W25Q32 には個別に選択できる4つのFPGAイメージを格納します。2個のはんだジャンパーが `CBSEL1:CBSEL0` を構成し、オープンは `0`、はんだブリッジは`1`です。ジャンパーを変更しても実行中のイメージには影響しません。新しい値は次回の電源レール・リセット時にだけ読み取られます。

| PIN  | イメージ | 役割                                               | フレーム・チャンネル |
| ---- | -------: | -------------------------------------------------- | ----------- |
| `00` |        0 | 保護されたブートローダー、書き込み、復旧用イメージ | BOOTとFLASH |
| `01` |        1 | 標準の製品用アプリケーション                       | BOOTとUART  |
| `10` |        2 | 代替ユーザーアプリケーション                       | BOOTとUART  |
| `11` |        3 | 代替アプリケーションまたは診断                     | BOOTとUART  |

開発時は通常、両方のジャンパーをオープンにします。製品用基板では通常ビット0を
ブリッジし、ホストがなくてもイメージ1が起動するようにします。

## コールドブート

1. USB VBUS から基板へ給電します。`RESET` を離すと3.3 Vと1.2 Vのレギュレーターが有効になり、両方の電源レールが放電された状態から立ち上がります。
2. iCE40 のコンフィグレーション・コントローラーが、フラッシュアドレス `0x000000` にあるコールドブート・アプレットとベクターテーブルを読み取ります。
3. コントローラーが `CBSEL1:CBSEL0` をサンプリングし、ベクターテーブルから選択されたイメージのアドレスを読み取ります。
4. 値が `00` ならイメージ0をロードします。`01`、`10`、`11`なら、それぞれイメージ1、2、3を直接ロードし、先にイメージ0を実行することはありません。
5. 有効なコンフィグレーションのロードが完了すると、オープンドレインの `CDONE` ピンがプルアップによってHighレベルになります。
6. 選択されたイメージが48 MHzのUSBロジックを初期化し、制御可能なD+プルアップを有効にします。すべてのイメージが同じCDC ACM識別情報とエンドポイント構成で列挙されます。

イメージ0は橙色の `PROG` LEDを点灯し、ホストからのコマンドを無期限に待ちます。タイムアウトでユーザーイメージへ移行することはありません。イメージ1～3は `PROG` を消灯し、共通のBOOTマネージャーとフレーム化UARTバイトストリームを提供します。

## ブートに関係するUSBトランスポート

すべてのイメージが1個のCDC ACMシリアル機能を公開します。EP1 INはCDC通知、EP2 OUT/INは
フレーム化バイトストリームです。各フレームのチャンネル番号によってBOOT、FLASH、UARTを
分離し、互いのpayloadを検査しません。

| チャンネル | イメージ0 | イメージ1～3 |
| --- | --- | --- |
| BOOT（`0x01`） | 利用可 | 利用可 |
| FLASH（`0x02`） | 利用可 | 利用不可 |
| UART（`0x03`） | 利用不可 | 利用可 |

GET_INFOが実行中イメージとcapabilityを返します。USB descriptor、VID/PID、Product、
Serial Numberは全イメージで同じです。

## ホスト要求によるウォームブート

すべての有効なイメージが共通のBOOTサービスを実装します。ウォームブートは
コールドブートと同じ4個のベクターテーブル・エントリーを選択しますが、
`SB_WARMBOOT`への内部信号 `S1:S0` を使用し、外部のはんだジャンパーは
再サンプリングしません。

1. ホストがCDCストリームへ、対象イメージ`0`～`3`を1バイト含むフレーム化BOOT
   SELECT_IMAGEコマンドを送信します。
2. 実行中のイメージがイメージ番号と切替先のマニフェストを検証します。フレーム化
   レスポンスは次のステータスを1バイト返します。

   | ステータス | 意味                     |
   | ---------: | ------------------------ |
   |        `0` | 要求を受理               |
   |        `1` | イメージ番号が不正       |
   |        `2` | 切替先マニフェストが不正 |
   |        `3` | マネージャーがビジー     |

3. 要求を受理した場合、USBやQSPIを停止する前に完全なレスポンス・フレームとCDC IN転送を完了します。
   これにより、ホストは後続のUSB切断だけに頼らず、明示的な応答を受け取れます。
4. マネージャーは新しいQSPI処理を禁止し、実行中の処理完了とフラッシュのWIPビットが
   クリアされるのを待ち、通常の1ビットSPIコマンドモードへ戻してフラッシュの
   `/CS`をHighレベルにします。
5. マネージャーがUSBを切断し、対象を `S1:S0` に登録した後、別のクロックで
   `SB_WARMBOOT`をアサートします。再コンフィグレーションによって現在のロジックが
   消去されるまで`BOOT`をアサートし続けます。
6. コンフィグレーション・コントローラーが選択されたベクターをロードし、新しい
   イメージがUSBへ再接続し、同じUSB識別情報で再列挙されます。

現在実行中のイメージを選択した場合も、意図的にそのイメージを再起動します。
ウォームブートでは物理ジャンパーを変更しないため、次回の`RESET`では再び
ジャンパー値を使ってコールドブートします。コンフィグレーションをまたいで常駐する
USBブロックはないため、USBの切断と再列挙は意図した動作です。

## 開発時の書き込み手順

1. 両方のジャンパーをオープン（`00`）にして`RESET`を押します。イメージ0が起動して
   ブートローダーとして列挙され、無期限に利用可能な状態になります。
2. イメージ0のFLASHチャンネルを使い、選択したイメージ1、2、3のスロットだけを
   消去して、ビットストリームとマニフェストを書き込みます。
3. ブートを要求する前に、マニフェスト、CRC、フラッシュのリードバックのいずれか、
   または必要な組み合わせで検証します。
4. フレーム化BOOT SELECT_IMAGE `n`を送信します。受理応答の後、イメージ0が
   イメージ`n`へウォームブートし、ホストは同じCDCデバイスの再列挙を待ちます。
5. 再度書き込む場合は、ユーザーイメージのBOOTチャンネルからSELECT_IMAGE 0を送信し、
   GET_INFOがイメージ0を返すのを待ちます。

フラッシュを書き換える必要がない場合、ホストは`BOOT 1`、`BOOT 2`、`BOOT 3`を使って
有効なユーザーイメージ間を直接切り替えることもできます。

## フラッシュ配置

現在の計画では、4 MiBのW25Q32を4個の256 KiBイメージ領域と3 MiBのユーザーデータ
領域に分割します。これらのアドレスは現在のプロトコル定数と一致しますが、最終的な
ビットストリームとマルチブート・イメージを確認するまでは暫定です。

| フラッシュ範囲      |  サイズ | 内容                                          | 書き込み方針                   |
| ------------------- | ------: | --------------------------------------------- | ------------------------------ |
| `0x000000-0x03FFFF` | 256 KiB | コールドブート・テーブルと保護されたイメージ0 | 工場／復旧ツールのみ           |
| `0x040000-0x07FFFF` | 256 KiB | イメージ1                                     | イメージ0の書き込み機能のみ    |
| `0x080000-0x0BFFFF` | 256 KiB | イメージ2                                     | イメージ0の書き込み機能のみ    |
| `0x0C0000-0x0FFFFF` | 256 KiB | イメージ3                                     | イメージ0の書き込み機能のみ    |
| `0x100000-0x3FFFFF` |   3 MiB | ユーザーデータ                                | 明示的なユーザーデータ操作のみ |

工場出荷用イメージは256 KiB境界に揃えて作成します。

```bash
icemulti -c -a18 -o factory.bin image0.bin image1.bin image2.bin image3.bin
```

通常のUSB書き込みでは、イメージ0を消去または書き換えてはいけません。次回の
コールドブートでは通常のSPIコマンド・フレーミングが必要なため、ユーザーコードは
W25Q32を永続的なQPIモードのままにしてはいけません。

## RESET、外部書き込み、復旧

フロントパネルの`RESET`ボタンは電源レール・リセットであり、`CRESET_B`を直接操作する
リセットではありません。ボタンを押している間は`PWR_EN`を通して両方のレギュレーターを
無効にし、離すと電源レールが再起動してコールドブート選択を再度サンプリングします。
3.3 Vレールを外部から給電するとこの動作を迂回する可能性があるため、通常の使用方法
としてはサポートしません。

`CRESET_B`はプルアップされたまま、工場書き込みと最終的な復旧用として外部SPIヘッダー
J5へ接続されています。

1. USBから基板へ給電し、3.3 V対応のSPIプログラマーをJ5へ接続します。
2. `CRESET_B`をLowレベルにし、共有されているコンフィグレーション・ピンを
   ハイインピーダンスにします。
3. CS/SCK/MOSI/MISOを使って、工場出荷用マルチブート・イメージ全体を書き込み、
   検証します。
4. `CRESET_B`を解放します。FPGAがコールドブート・テーブルを読み取り、通常の
   ジャンパー選択によるコールドブート手順を実行します。

ユーザーイメージが不正、または`BOOT 0`を処理できない場合は、両方のジャンパーを
オープンにして`RESET`を押し、保護されたイメージ0を起動します。イメージ0または
コールドブート・テーブルが破損している場合は、上記の外部SPI手順で復旧します。
工場出荷用イメージには、有効な標準イメージ1と、未使用スロット用の安全な
マネージャー対応プレースホルダー・イメージを含め、どのベクターを選択しても
復旧可能な状態にします。

## ブート時のハードウェア制約

- コールドブート中は、共有されているコンフィグレーション・ピンK10（`/CS`）、
  L10（`SCK`）、K9（`IO0`）、J9（`IO1`）を外部から駆動してはいけません。
- コンフィグレーション完了後は、実行中のイメージが6本すべてのQSPI信号を使用します。
  ウォームブート前には、上記の手順どおりインターフェースを停止する必要があります。
- FPGAのE10ボールには基板上の48 MHz発振器が接続されているため、HDLではクロック入力の
  ままにする必要があります。
